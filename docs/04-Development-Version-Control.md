# OntologyOps 开发版本控制规则

> 状态：生效
>
> 来源：由项目负责人提供的 `agent-version-control-rules.md` 迁入本项目。本文是 OntologyOps 后续所有代码、配置、文档及部署变更的强制规则。

## 适用范围与前置条件

- 本规则仅约束 OntologyOps 项目；不应把项目外的临时文件、个人资料或其他项目纳入提交。
- 当前仓库尚未建立首次提交和远端。开始开发前，必须由项目负责人确认远端地址，并建立 `main` 与 `dev` 两个分支的初始基线；基线完成后，以下规则无例外执行。
- 文档评审阶段不触发部署；进入实现后，任何改动均执行本规则。

## 规则 1：每次改动必须 commit + push

- 无论改动大小（包括一个按钮颜色），改完后立即提交并推送至 `dev`：

  ```bash
  git add -A
  git commit -m "中文描述改了什么"
  git push origin dev
  ```

- 不允许跳过 commit 直接看效果或部署。
- commit message 必须使用中文，清楚描述改动内容。

## 规则 2：本地验收流程

- 本期不建设独立 staging 或测试服务器。`dev` 分支在本地运行，使用自动化测试、临时测试数据和浏览器验收完成验证。
- 每个模块在本地通过后，必须由项目负责人在浏览器中确认 UI 与功能；验收必须使用新上传的数据，不能以种子工厂数据代替。
- 获得“确认 OK”前，不得合并至 `main` 或进入下一模块。
- 确认后立即建立并推送本地验收标签：

  ```bash
  git tag local-YYYYMMDD-HHMM
  git push origin --tags
  ```

## 规则 3：确认基线（main）流程

- 本期不部署 production。`main` 仅保存已经由项目负责人本地确认过的稳定基线；不得从未推送状态或未经确认的 `dev` 直接标记为稳定版本。
- 流程如下：

  ```bash
  git checkout main
  git merge dev
  git tag release-YYYYMMDD-HHMM
  git push origin --tags
  ```

- 标记后在本地重新运行核心自动化测试和浏览器验收。未来需要部署生产时，另行增加环境、发布和审批规则。

## 规则 4：故障回滚

- 本地运行出现问题：检出上一个 `local-*` 或 `release-*` 标签，在独立本地目录重新运行验证。
- 禁止在故障状态中临时改代码“试试看”；先恢复到最近已确认的存档点，再分析与修复。

## 规则 5：仅保留两个长期分支

- `main`：正式环境，只能通过从 `dev` 合并进入，不直接修改。
- `dev`：测试环境，日常开发在此进行。
- 不创建额外长期分支，除非项目负责人明确要求。

## 一句话执行准则

**改代码必 commit → `dev` 本地自动化测试和浏览器验收 → 项目负责人确认后打 local tag → 合并到 `main` → 再次本地验证并打 release tag。每一步都有可回退存档。**
