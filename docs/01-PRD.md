## 0. 评审结论与开发门禁

本 PRD 的目的不是把工厂模板包装为平台，而是定义一条可验证的企业 AI 转型最小闭环：**新数据接入 → 可信数据集 → 已发布本体 → 受控语义工具 → 有证据的智能助手 → 完整追溯与治理**。

在产品负责人确认本 PRD 前：

- 不开始高保真原型、技术方案或代码实现。
- 不接受预置工厂数据、固定血缘、固定风险答案、固定状态标签作为平台能力证据。
- 不把任何页面完成、接口存在或单元测试通过标为“验收通过”。验收必须以浏览器中导入的全新数据完成端到端场景。

## 1. 产品背景、愿景与定位

企业 AI Native 转型的障碍通常不在于缺少大模型，而在于数据、业务语义、权限、计算口径和应用行为之间没有可信的统一接口。表、字段和 SQL 无法直接成为业务人员和 Agent 稳定协作的产品语言。

OntologyOps 是一个面向企业 AI 转型方法论的本地学习型 MVP。它借鉴数据集成、本体、AI 应用和安全治理的分层思想，验证一件事：企业能否把实际导入的数据和文档转为受版本、权限、质量与证据约束的业务语义资源，并只让 Agent 经这些资源回答问题。

它不是 Palantir Foundry、AIP 或完整数仓的替代品，也不是轻量“上传文件 + 聊天”的 AI SaaS。

### 1.1 产品目标

1. 证明同一平台可从不同领域的结构化数据与文本资料创建新的本体，而非只能展示工厂模板。
2. 以工厂采购为首个演示领域，使用新上传的订单、供应商、物料、库存、质检数据跑通可信智能助手闭环。
3. 让每一个 Agent 结论能够回溯到本体版本、已发布资源、查询工具、映射、管道运行、数据集与源文件/源表。
4. 把本体建模、数据质量、访问策略与 Agent 工具约束设计为同一资源链，而非并列的展示页面。

### 1.2 非目标

- 不构建通用数据仓库、湖仓、通用 BI、拖拽式报表、风险驾驶舱或数字孪生应用。
- 不构建写回、审批、自动 Action、任务编排、事件触发、Webhook 或系统自动决策。
- 不做本体分支、合并、多人实时协作、生产级多租户或部署控制平面。
- 不支持扫描件 OCR；只处理可直接提取文本的 PDF 与 `.docx`。
- 不支持自由 text-to-SQL、Agent 直连底层表，或通过提示词绕过资源和字段权限。
- 模型管理本期支持 GPT、DeepSeek、管理员显式添加的 OpenAI 兼容 API 与明确标识的 Mock 测试模式；真实模型只能在本机密钥验证后启用。

## 2. 官方概念对照与 MVP 边界

| 能力层 | 官方概念的可借鉴定义 | OntologyOps v1 必做 | 明确不做 |
| --- | --- | --- | --- |
| 数据底座 | 接入、转换、数据质量、版本与血缘让数据可被可靠使用 | 文件/文档导入、数据集、受控手动管道、质量规则、运行记录和血缘资源 | 分布式计算、流式、调度、完整连接器市场 |
| 本体 | 覆盖对象、属性、Link 等语义元素，并承接函数、规则等动能元素 | 对象、属性、Link、映射、指标、函数、规则、草稿/发布/回滚、候选审核 | Action、写回、审批、外部系统编排 |
| AIP / 应用 | 在受安全、审计、资源管理约束下把 AI 建在本体之上 | GPT/DeepSeek/Mock、模型路由、受控问数 Agent、工具调用审计与证据输出 | 通用 Agent 搭建器、知识库产品、自动工作流 |
| 安全与治理 | 身份、资源权限、细粒度数据访问、审计与可解释性贯穿运行 | 单租户角色、资源/对象/字段策略、权限拒绝、审计与证据链 | SSO、企业 IAM、完整行级/列级策略引擎、多组织隔离 |

本体是业务语义、权限和可解释性的统一接口；它不替代数据存储、转换或大规模聚合计算。需要聚合时，运行时可调用**已发布指标定义所绑定的受控计算路径**，但 Agent 永不生成或执行自由 SQL。

## 3. 产品原则与不可妥协的验收规则

1. **资源链为真。** 数据源、数据集、管道节点、质量规则、映射、本体版本、指标/函数/规则、策略和 Agent 工具调用必须能被唯一标识并建立依赖关系。
2. **发布即边界。** 草稿资源只用于编辑和验证；应用与 Agent 仅能发现、调用当前已发布本体版本中的资源。
3. **候选不是事实。** AI 建模输出必须带来源、置信度和待确认问题；接受、拒绝、编辑均须形成草稿变更记录。
4. **治理先于模型。** Agent 取得上下文、生成工具计划与返回答案前均执行已发布策略；拒绝同样可审计。
5. **证据与结论同送达。** 任何可验证答案同时返回结论、使用的工具与参数、数据集/更新时间、本体版本、指标口径及可展开对象证据。
6. **先数据后模板。** 工厂数据只作为示例包，不能充当对上传数据链路的兜底答案。
7. **低承诺 MVP。** 仅交付受控读与人工决策支持；未来 Action 必须另立阶段，并具备授权、审计、回滚和副作用控制设计。

## 4. 用户、角色与核心任务

| 角色 | 首要任务 | 本期权限边界 |
| --- | --- | --- |
| 平台管理员 | 配置模型、角色与资源策略；查看全局审计 | 管理全部资源与策略；不代表可绕过审计 |
| 本体建模者 | 导入数据，创建可信数据集与本体草稿，审核和发布 | 管理数据、管道、本体草稿；不能管理模型密钥与全局角色 |
| 业务分析者 | 基于已发布本体提问、查看证据和人工建议 | 仅调用被授权对象、字段、指标、规则和 Agent 工具 |

首个目标问题：

> “本月哪些供应商的订单最容易延期，且可能影响关键物料库存？请说明证据与数据口径。”

该问题不是固定问答。只有当用户上传的数据已通过指定映射、发布了相关对象/Link/指标/规则，且角色被授权时，Agent 才可调用对应工具并生成回答。

## 5. 统一资源模型与生命周期

### 5.1 资源类型

| 类别 | 资源 | 必需标识与关键字段 |
| --- | --- | --- |
| 数据 | DataSource、SourceAsset、Dataset、DatasetVersion | ID、名称、类型、schema、来源位置、owner、创建时间、状态 |
| 管道 | Pipeline、PipelineNode、PipelineRun、NodeRun | ID、节点类型、输入/输出资源、配置版本、运行状态、行数/错误 |
| 质量 | QualityRule、QualityRun、QualityFinding | 目标数据集版本、规则表达式、结果、异常样本引用 |
| 本体语义 | Ontology、OntologyDraft、OntologyRelease、ObjectType、Property、LinkType、Mapping | 稳定 ID、显示名、描述、定义、依赖资源、版本、状态 |
| 本体动能 | Metric、Function、Rule | 输入对象/属性/Link、受控表达式或实现引用、输出契约、依赖资源 |
| 治理 | AccessPolicy、AuditEvent、LineageEdge | 主体、资源/字段范围、允许操作、决策、事件发起者与时间 |
| AI | ModelProvider、ModelProfile、AgentSession、ToolRegistry、ToolCall | 模型模式、工具来源资源、策略决策、参数、结果摘要、证据引用 |

### 5.2 状态机

| 资源 | 合法状态与转换 |
| --- | --- |
| 数据集版本 | `registered → profiled → trusted / rejected`；仅 `trusted` 可作发布映射输入 |
| 管道运行 | `queued → running → succeeded / failed / cancelled`；失败不得生成可用输出 |
| AI 候选 | `proposed → accepted / rejected / superseded`；接受后才写入草稿 |
| 本体草稿 | `editing → validation_failed / ready_to_publish → published`；发布产生不可变 release |
| 本体发布版本 | `published → superseded / rolled_back`；回滚是切换当前 release，不篡改历史 |
| 模型配置 | `mock / configured / verified / disabled / error`；非 `verified` 的外部模型不得被默认调用 |
| Agent 工具调用 | `planned → authorized / denied → executed / failed`；每次均产生审计事件 |

### 5.3 最小可追溯链

```text
SourceAsset → DatasetVersion → PipelineNodeRun → QualityRun
→ Mapping → OntologyRelease → {Object / Property / Link / Metric / Function / Rule}
→ ToolRegistryEntry → ToolCall → AgentAnswer → AuditEvent
```

任何链条断裂时，UI 必须显示“证据不完整”及缺失节点，不能伪造完整血缘。

## 6. 信息架构与界面原则

### 6.1 一级导航

| 导航 | 目的 |
| --- | --- |
| 工作台 | 当前本体、发布状态、待处理候选/质量失败/最近活动；不做风险驾驶舱 |
| 数据与管道 | 数据源、资产、数据集、管道、运行与质量 |
| 本体管理 | 对象、属性、Link、映射、指标、函数、规则、候选、发布历史 |
| 智能助手 | 单一的受控 Copilot 应用与会话审计；当前能力聚焦智能问数、关系追溯、证据解释与人工建议。 |
| 治理与可追溯 | 策略、质量结果、资源血缘、审计 |
| 模型管理 | GPT、DeepSeek、Mock 的配置、验证、路由与调用记录 |

### 6.2 视觉和交互原则

- 简约现代风：留白、清晰层级和克制的科技感；同时保持业务页面所需的数据密度。
- 界面以对象关系、状态、证据与可追溯性为主，不沿用旧原型风格，也不以装饰性视觉替代信息表达。
- 每个资源详情采用“状态 + 定义 + 依赖 + 影响 + 历史”结构，而不是孤立卡片。
- 颜色仅表达状态或风险；每个状态必须有可读文字与可追溯原因。
- 没有真实资源时展示空状态与下一步，不展示工厂预填内容冒充用户数据。

## 7. MVP 模块需求

### M0. 资源注册与关系内核（平台前置能力）

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 让每个后续模块创建的资源都可标识、关联、版本化与审计。 |
| 输入 → 输出 | 创建/变更资源与依赖声明 → 资源 ID、版本、状态、关系边、审计事件。 |
| 页面与状态 | 不单独作为业务页面；资源详情页和治理页可查看 ID、状态、依赖与影响。 |
| 真实操作 | 持久化资源、校验引用存在性、拒绝无效状态转换、写入变更审计。 |
| 依赖 | 所有模块依赖 M0。 |
| 不做 | 通用元数据目录、跨租户共享、复杂工作流引擎。 |
| 浏览器验收 | 上传一个新文件后，在详情页取得 DatasetVersion ID；后续管道、本体和 Agent 回答均可从该 ID 追溯。 |

### M1. 数据接入、数据集与受控管道

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 导入 CSV、Excel、可提取文本的 PDF/DOCX，理解 schema，手动转换为可用数据集。 |
| 输入 → 输出 | 文件或文件内表 → SourceAsset、DatasetVersion、字段 profile、文档文本资产；管道配置 → 输出 DatasetVersion。 |
| 资源模型 | DataSource、SourceAsset、DatasetVersion、Pipeline、PipelineNode、PipelineRun、NodeRun。 |
| 页面与状态 | 数据源列表/详情、导入向导、数据集预览、管道画布与运行详情；明确 `registered/profiled/trusted/rejected` 和运行状态。 |
| 真实操作 | 上传、解析、schema/profile 生成；字段重命名、选择、类型转换、空值处理、去重、过滤；运行后生成真实输出和统计。 |
| 跨模块依赖 | 为质量、映射、候选生成和血缘提供真实输入；映射只能选择 trusted 版本。 |
| 不做 | MySQL、通用数据库连接器、调度、流式、任意代码节点；本期先保证文件数据端到端真实。 |
| 浏览器验收 | 上传一份从未出现过的供应商/订单 CSV，完成至少一项转换，在预览中核对输出值、行数和运行记录。 |

### M2. 数据质量与可信数据集

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 对目标数据集设置并运行质量规则，决定其是否可被本体映射使用。 |
| 输入 → 输出 | DatasetVersion + 规则配置 → QualityRun、通过率、异常样本、可信/拒绝决策。 |
| 资源模型 | QualityRule、QualityRun、QualityFinding；规则必须绑定具体 DatasetVersion/字段。 |
| 页面与状态 | 数据集质量标签、质量规则列表、运行结果和异常样本；`not_run/pass/warn/fail`。 |
| 真实操作 | 至少支持完整性、唯一性、值域与跨字段一致性；对上传数据实际执行并保存样本。 |
| 跨模块依赖 | 通过的数据集版本才可被 M3 映射；质量结果进入血缘和 Agent 证据。 |
| 不做 | 自动修复、持续监测、复杂统计异常检测。 |
| 浏览器验收 | 上传含空供应商编码和重复订单号的数据，运行规则并看到对应异常样本；未经处理的数据不能被选择为发布映射源。 |

### M3. 本体管理与 AI 辅助建模（首个详细确认模块）

#### M3.1 用户任务

本体建模者以可信数据集和可选文档资产为证据，定义并发布可运行的业务语义：对象、属性、Link、映射、指标、函数和规则。AI 只能提出候选，不能替代审核者发布。

#### M3.2 语义与动能资源定义

| 资源 | 必需定义 | 运行含义 |
| --- | --- | --- |
| ObjectType | 稳定 ID、名称、业务描述、主键、显示名、数据来源、状态 | 可被查询、被授权、被 Agent 引用的业务对象集合，如 `Supplier`。 |
| Property | 所属对象、名称、业务定义、类型、是否主键/显示字段、来源字段、敏感级别 | ObjectType 的可查询业务属性；技术列可被隐藏，不自动等同业务属性。 |
| LinkType | 起点/终点对象、名称、方向、基数、语义描述、两端映射 | 可控关系遍历，如 `PurchaseOrder — SUPPLIED_BY → Supplier`。 |
| Mapping | DatasetVersion、源字段/条件、目标资源、转换规则、mapping version | 将真实数据投影为对象、属性或 Link 的可追溯配置。 |
| Metric | 业务定义、作用对象、输入资源、计算口径、受控表达式/函数引用、输出类型 | 经发布后可供 Agent 调用的指标，而非页面硬编码数值。 |
| Function | 名称、描述、参数/返回契约、依赖资源、只读实现引用、授权范围 | 封装可复用的复杂读计算；本期不具副作用。 |
| Rule | 条件、输入资源、输出标签/对象集合、阈值/版本、解释模板 | 在已发布数据上计算业务判定，如“关键物料供应风险”。 |

#### M3.3 候选、草稿、发布与回滚

1. 建模者选择一个或多个 trusted DatasetVersion，并可选择已解析文档资产。
2. 系统把选定 schema、有限样本和文档片段传入建模辅助流程，生成**有来源引用**的 `proposed` 候选与待确认问题。
3. 建模者逐项接受、拒绝或编辑；每个决定写入 OntologyDraft 及审计。
4. 系统校验：主键存在、属性来源有效、Link 两端可解析、指标/函数/规则仅引用草稿内合法资源、映射数据集仍可信。
5. 校验通过后展示发布影响：将新增/移除/改变的资源、受影响映射、工具与策略。
6. 发布产生不可变 OntologyRelease，并从该 release 编译对象投影、受控工具和血缘边。
7. 回滚只把“当前发布版本”切换至旧 release；历史版本、审计和数据集版本保留。

#### M3.4 页面、状态与真实操作

| 页面 | 必须可做的真实操作 | 禁止的伪能力 |
| --- | --- | --- |
| 本体列表/概览 | 新建草稿、查看当前 release、进入版本历史 | 用预置对象数量/状态代替真实版本 |
| 对象与属性编辑器 | 创建/编辑/删除草稿对象属性；选择主键与显示名；从可信字段建立映射 | 自动把全部源列 1:1 映射为业务属性 |
| Link 编辑器 | 选择两端 ObjectType、方向和基数；配置可验证的关联字段/条件 | 固定工厂关系图或无映射的边 |
| 指标/函数/规则编辑器 | 定义只读依赖、口径、受控表达式或实现引用；预览运行结果 | 固定风险文案或未经发布的自由代码 |
| 候选审阅 | 查看候选证据、置信度、问题；接受/拒绝/编辑并记录原因 | “生成成功”后直接填充工厂模板 |
| 发布中心 | 执行验证、查看影响、发布、查看 release、回滚 | 仅改变 badge 或前端状态 |

#### M3.5 跨模块依赖与不做项

- 输入依赖 M0 的资源关系、M1 的真实数据集和 M2 的可信决策。
- 输出为 M4 的政策编译范围、M5 的 Agent 工具注册表和 M6 的证据/血缘节点。
- 本期不做 Action type、写回、审批、多分支合并、复杂本体继承/interface、跨本体共享库、自由图查询语言。

#### M3.6 浏览器验收用例

使用新上传的非种子 CSV（至少 Supplier、PurchaseOrder、Material、Inventory 四类数据）：

1. 在通过质量规则的数据集上，创建 `Supplier`、`PurchaseOrder`、`Material`、`Inventory` 四个 ObjectType，并将各自主键/属性绑定到实际字段。
2. 创建 `PurchaseOrder — SUPPLIED_BY → Supplier` 与订单至物料的 Link，保存关联条件。
3. 生成或手工创建“延期风险订单数”指标和“关键物料供应风险”规则，并展示其读取的实际资源。
4. 对至少一个 AI 候选执行接受、一个执行拒绝，刷新页面后决定与来源仍存在。
5. 发布 v1；修改一个属性/规则形成 v2 并发布；回滚到 v1 后，当前 release 与可用工具集同步恢复。

### M4. 治理、策略、血缘与审计

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 管理员可定义角色对发布资源的可见/可调用范围，并解释一个结论的上下游链。 |
| 输入 → 输出 | 角色/资源/字段策略与资源依赖 → 授权决策、LineageEdge、AuditEvent。 |
| 资源模型 | AccessPolicy、LineageEdge、AuditEvent，均引用具体资源版本。 |
| 页面与状态 | 策略编辑、授权模拟、血缘浏览、审计时间线；显示 allow/deny 与原因。 |
| 真实操作 | 对页面读取、Agent 工具发现、工具执行和结果字段统一执行策略；从映射/运行/发布/调用自动汇集血缘。 |
| 跨模块依赖 | 读取 M0-M3 的关系；约束 M5/M6 的模型和工具访问。 |
| 不做 | 企业身份集成、跨组织共享、策略脚本语言、导出/下载控制。 |
| 浏览器验收 | 将“合同单价”限制给管理员；业务分析者在对象页、Agent 提问与证据展开三处均无法看到，且审计出现同一策略 ID 的拒绝。 |

### M5. 模型管理

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 管理员选择 DeepSeek V4 Flash / V4 Pro、GPT 或兼容 API，验证连接并明确每次调用使用的模型。 |
| 输入 → 输出 | Provider 配置/密钥引用、模型参数、用途 → ModelProfile、验证结果、调用记录。 |
| 资源模型 | ModelProvider、ModelProfile、ModelInvocation；密钥不写入审计、页面或导出。 |
| 页面与状态 | Provider/模型列表、配置、连通性验证、按“建模/问数”用途的路由与调用记录；状态见 5.2。 |
| 真实操作 | DeepSeek 使用 `deepseek-v4-flash` 或 `deepseek-v4-pro` 发起无提示词的连通性验证；Mock 只能返回带 `mock=true` 的结构化响应；失败要可见且不得伪装成功。 |
| 跨模块依赖 | 为 M3 候选生成和 M6 回答提供模型；M4 管理谁可配置/使用。 |
| 不做 | 除 OpenAI 兼容 HTTP API 外的其他 Provider 协议、模型训练、微调、成本结算、自动模型选择。 |
| 浏览器验收 | 无密钥时运行 Mock 且界面清晰标识；配置可用模型后验证成功；停用模型后建模/问数不得再选择它。 |

### M6. 智能助手（Copilot，唯一应用层）

| 项目 | 需求 |
| --- | --- |
| 用户任务 | 与当前发布本体上的 Copilot 对话，提出自然语言业务问题，获得可信结论、证据和人工建议。 |
| 输入 → 输出 | 用户问题 + 角色 + 当前 OntologyRelease → 工具计划、授权结果、工具结果、回答、证据包、审计。 |
| 资源模型 | AgentSession、ToolRegistryEntry、ToolCall、AgentAnswer；工具只能由已发布 Object/Property/Link/Metric/Function/Rule 编译而来。 |
| 页面与状态 | 对话、工具调用折叠区、证据抽屉、版本/口径/更新时间、权限拒绝提示；`planned/authorized/denied/executed/failed`。 |
| 真实操作 | 将问题路由为受控对象过滤、Link 遍历、指标、函数、规则查询；参数校验与授权后执行；把结果和来源组成答案。 |
| 跨模块依赖 | 严格依赖 M3 release 的工具注册、M4 策略/M0 血缘、M5 模型配置。 |
| 不做 | 自由 SQL、外部系统调用、写回、自动处置、任务执行、固定风险问答。 |
| 浏览器验收 | 上传并发布一套新数据后，询问目标问题；答案中的供应商、订单、库存和指标结果均与上传数据一致，工具调用与证据可逐层回溯至 SourceAsset。 |

## 8. 端到端验收场景

### E2E-01：从新数据到可信问数

1. 管理员启用 Mock 或已验证 GPT/DeepSeek 模型。
2. 建模者上传新 CSV 文件；至少一个供应商名称、订单编号和库存数值不能出现在任何种子数据中。
3. 建模者完成转换，运行质量规则，修复或拒绝不可信数据版本。
4. 建模者创建/审核本体资源和映射，发布 OntologyRelease。
5. 业务分析者提问目标问题，Agent 仅调用该 release 注册的已授权工具。
6. 用户从回答展开证据，看到数据集版本、字段映射、指标/规则口径、工具调用、本体版本和质量结果。
7. 管理员在审计页看到完整资源链与权限决策。

**通过条件：** 修改上传数据中的订单日期、库存或供应商字段后，重新运行并发布，Agent 结论和证据必须随之改变；任何固定工厂答案均视为失败。

### E2E-02：权限拒绝一致性

1. 管理员在已发布本体中将一个敏感属性设为仅管理员可见。
2. 业务分析者在对象页、指标/规则证据、Agent 结果中均不可读取该属性。
3. 对相同属性的 Agent 请求被拒绝或自动裁剪；审计记录资源、策略、主体与决策。

### E2E-03：发布与回滚

1. 基于发布 v1 修改一个属性、映射或规则，形成 v2 草稿。
2. 发布 v2 后，工具注册与 Agent 证据显示 v2。
3. 回滚到 v1 后，Agent 不再使用 v2 的资源；历史的 v2 调用仍可在审计中追溯。

## 9. 非功能要求

- 所有关键页面必须区分“无数据、草稿、运行中、成功、失败、拒绝、权限不足”。
- 资源 ID、版本、时间、发起者和依赖至少在详情/证据/审计之一可见。
- 前端不保存 API Key；日志与证据不输出密钥或未授权原始字段。
- 任一资源删除/失效后，引用方要显示失效依赖，不能静默回退到种子定义。
- 本地单租户优先可理解、可验证与可恢复；不以虚假的通用性换取页面数量。
